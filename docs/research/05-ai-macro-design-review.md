# AI 매크로 방어 설계 검토

작성일: 2026-10-13 · 대상: 팀 설계서 "규칙 진화형 AI 매크로 방어"(작성 기준일 2026-10-07)와 노션 "매크로 ai 문헌조사"

아직 구현하지 않았고, 검증도 시작하지 않았다. 이 문서는 나중에 검증할 것을 전제로 설계를 점검한 결과다.

## 1. 설계의 강점 (유지)

- **AI가 직접 차단하지 않고 사람이 읽을 수 있는 규칙을 만든다.** 판정 경로에 모델을 넣지 않는 이유(지연), 개정 공연법의 기술적 조치 의무(근거 기록·재현), 오탐 책임(운영자 승인)을 모두 설명할 수 있다.
- **도착 시각을 모든 검사보다 먼저 찍는다.** "탐지가 정상 사용자의 순서를 바꾸지 않는다"를 실험으로 증명하기 쉽다.
- **거주지 연관 피처 금지**(지역, PoP, IP·ASN 대역, RTT, 시계 오프셋). 지방 사용자를 위한 시스템이 지방 사용자를 봇으로 모는 일을 막는다. 프로젝트 목적과 직결되므로 발표에서 강조한다.
- **정직한 평가 틀:** 봇 사다리 L0~L5, 정답·약한 라벨 분리, 신뢰 상한 보고. 노션 문헌조사와 일관된다.

## 3. 설계가 놓친 기술적 함정

1. **HTTP 사이트에서는 핵심 신호를 쓸 수 없다.** `Sec-Fetch-*`, `Sec-CH-UA`(Client Hints)는 브라우저가 보안 연결에서만 보낸다. HTTP에서 이 규칙을 켜면 정상 사용자 전원이 걸린다. JA4는 TLS가 없어 계산 불가. → 6절 참고.
2. **학습 재료가 로그에 없다.** `detection-log`에는 IP·UA·계정·기기·계정 나이만 있다. 헤더 전체, 1차 필터 결과·사유, 규칙셋 버전, µs 도착 시각, 오픈 대비 반응 시간이 없다. Kafka 보존 7일이 지나면 사라지므로 수집 항목을 먼저 정해야 한다. `client_ip`가 위조 가능한 X-Forwarded-For 첫 값을 쓴다(리뷰 5번 항목) — 피처 오염.
3. **기기 지문은 브라우저가 계산해 보내는 값이다.** 봇은 매번 다른 값을 보낼 수 있어 "기기당 계정 수" 규칙은 L5(다계정)에 쉽게 뚫린다. 시연 시나리오가 이 약점에 너무 기대고 있다.
4. **PoP가 이미 병목이다**(초당 약 2,140건, [01-load-test.md](01-load-test.md)). 규칙 엔진 오버헤드 실험(F)이 필수다. 빈도 카운터 공유는 PoP별 로컬 Redis로 하고, 지역에 흩어진 봇은 2차(중앙)에서 잡는다. 대전 PoP가 요청마다 판교 Redis를 다녀오면 안 된다.
5. **마우스 데이터를 수집하지 않는다.** "SapiMouse 분포로 사람 시뮬레이터"는 우리 피처와 연결되지 않는다. 행동 텔레메트리를 넣거나 문장을 뺀다.

## 4. 우리 코드에 넣는 방법

**1차 (PoP)**
- `pop/first_layer.py`의 하드코딩 규칙을 규칙 JSON으로 옮기고 작은 평가기를 붙인다.
- 모든 결과에 `ruleset_version`, `rule_id`를 붙여 `detection-log`에 남긴다.

**2차 (central)**
- 요청 수신 시 계정 상태를 Redis 카운터로 갱신(계정이 노린 좌석 수, 기기당 계정 수)하고 규칙을 평가해 요청마다 `ok/defer/block` 표시를 붙인다.
- 창 마감 Lua를 "가장 빠른 1명"에서 **"block이 아닌 가장 빠른 1명"**으로 바꾼다. 보정 시각 순서는 그대로라 순서 불변이 구조적으로 보장되고, 같은 로그·같은 규칙셋이면 같은 승자(결정적 재현)가 나온다.

**DEFER와 차순위 승계**
- 확정 기록에 경쟁자 상위 40명이 이미 저장된다(`ALL_REQUESTS_KEEP=40`). "확정 후 N초 결제 보류 → 재평가 → block이면 다음 사람에게 승계"를 작게 구현할 수 있다. 시뮬레이션 대안보다 시연 효과가 크다.

**3차 (서울)**
- `collector.py` 로그 → 계정별 피처 → 규칙 후보 → 저장 로그 재현 리포트 → 승인 CLI.
- "깊이 3 트리면 if문 아니냐"는 질문 대비: **트리 앙상블(RandomForest/LightGBM)로 놓친 봇을 찾고, 깊이 3 규칙으로 압축해 배포**한다. 운영자 리포트에는 SHAP 근거를 붙인다. 두 문서(설계서의 규칙 채굴 + 노션의 RF/LightGBM+SHAP)의 장점을 합친 형태.

## 5. 나중의 검증을 위해 지금 설계에 넣을 것

1. **사전 등록:** 승격 게이트 기준값, 실험 절차, 2라운드 변형 봇 정의를 실험 전에 git에 커밋한다. 커밋 시각이 "결과를 보고 기준을 바꾸지 않았다"는 증거가 된다.
2. **라벨은 로그 밖에:** "이 계정은 참가자 7번 / L3 봇 2번" 정답표는 별도 파일로 관리한다. 로그·헤더에 표시를 넣으면 누수가 생긴다.
3. **봇 작성자와 규칙 작성자 분리:** 2라운드 변형 봇은 채굴 규칙을 보지 않은 팀원이 만든다(순환성 방지).
4. **격리 환경에서 실험:** 운영 시스템이 아닌 별도 환경, 데이터셋은 해시로 버전 고정.
5. **학습하지 않은 봇 수준으로 평가:** 예: L0~L2로 학습, L3로 평가.
6. **사람 참가자 20~30명 모집이 최대 일정 위험.** 30명이면 오탐 0건이어도 95% 신뢰 상한은 약 10% — 함께 보고한다.

## 6. HTTPS가 필요한가

꼭 필요하지는 않다. HTTPS 없이도 탐지는 만들 수 있다. 다만:

| 신호 | 알려주는 것 | HTTP에서 |
|---|---|---|
| `Sec-Fetch-*` | 사람이 눌러서 온 요청인지 스크립트 요청인지 | 브라우저가 안 보냄 |
| `Sec-CH-UA` | 브라우저 종류·버전(UA와 대조) | 안 보냄 |
| TLS 지문(JA4) | 진짜 브라우저인지 라이브러리인지 | TLS 없음 |
| `navigator.deviceMemory` | 기기 지문 재료 | 못 읽음 |

- HTTP로 가면 L0(curl), L5(다계정)는 잡히지만 L1~L2(Playwright, UA 위조)를 잡을 수단이 크게 줄어든다.
- 그 밖의 이유: 비밀번호·JWT가 평문 전송(토큰 탈취 시 계정 단위 탐지가 무력화), 비밀번호 입력 페이지의 브라우저 "주의 요함" 경고.
- `login.html`은 HTTPS면 SHA-256, HTTP면 FNV로 기기 지문을 만든다. 같은 기기라도 전환 전후 지문이 다르므로, 전환한다면 데이터 수집 전에 한다.
- 방법: `daejeon.doon.land` 등 이름 + Let's Encrypt 인증서. 포트를 열 필요 없는 DNS 인증(Cloudflare API 토큰) 사용, Cloudflare 프록시는 계속 끔(DNS only).
