1. 목적과 원칙

DOON은 선착순을 깨는 두 가지 불공정을 다룹니다. 거리의 차이는 엣지 스탬핑으로, 도구의 차이(매크로)는 이 계획으로 없앱니다. 1등이 봇이면 시각을 아무리 정밀하게 찍어도 공정하지 않기 때문입니다.

  • 도착 시각을 모든 검사보다 먼저 찍습니다. 탐지는 "자격"만 판단하고, 정상 사용자 사이의 순서는 바꾸지 않습니다.
  • 실시간 판정 경로에는 AI 모델을 넣지 않습니다. 지역 격차를 1~3ms 단위로 보정하는 시스템이 스스로 수 ms 지연을 만들면 안 됩니다. 규칙은 요청당 µs 단위로 끝납니다.
  • AI의 산출물은 읽을 수 있는 규칙입니다. 개정 공연법(2026-08-28 시행)이 예매처에 요구하는 "근거 기록·재현"을 설명할 수 있습니다.
  • 사는 곳과 연관된 피처는 금지합니다. 지역, PoP, IP·ASN 대역, RTT, 시계 오프셋. 지방 사용자를 위한 시스템이 지방 사용자를 봇으로 몰면 안 됩니다.

AI는 "판사"가 아니라 "규칙 만드는 연구원" 역할입니다. 판정은 규칙이 하고, 그 규칙을 계속 새로 만들고 고치는 게 서울의 AI입니다.

4. AI 구성 (보강안)

"결국 if문 아니냐"는 지적에 대비해 설계서를 보강합니다. 모델은 서울에서 제대로 돌리고, 판정에는 검증된 규칙만 내려보냅니다.

보강내용왜우선순위
① 모델 → 규칙 압축LightGBM으로 학습하고 SHAP으로 근거를 뽑은 뒤 깊이 3 규칙으로 압축(모델 증류). "규칙이 모델이 잡은 봇의 몇 %를 그대로 잡는지"(충실도)를 수치로 제시AI가 실제로 있음을 성능 수치로 증명필수
② 전국 PoP 묶음 탐지서울에 모인 전국 로그에서 같은 기기, 같은 시점 패턴, 같은 좌석 패턴을 공유하는 계정 그룹을 클러스터링. 대전·판교로 나눠 들어온 다계정 조직을 찾음한 PoP에서는 안 보이고 KOREN으로 모아야만 보임. 프로젝트 목적과 직결권장
③ 결제 보류 구간에서 모델 점수 활용확정 후 결제 전 시간에 서울 모델 점수를 재평가 근거로 함께 봄. 최종 결정은 규칙과 운영자AI가 리포트만이 아니라 판정에 참여. 실시간 경로가 아니라 지연 없음결제 보류 구현 시
④ 진화를 숫자로1라운드 봇 점유율 X% → 규칙 학습 → 2라운드 Y%"단순한데 효과가 있다"는 가장 강한 답필수

하지 않을 것

  • 실시간 판정 경로에 딥러닝 모델 넣기
  • "정확도 99%" 같은 숫자 하나로 주장하기 → 봇 수준별로 어디서 잡히고 어디서 놓치는지 공개
  • JA4(TLS 지문), 마우스·키 입력 수집, 자동 강등, 온라인 섀도 자동화 → 최종평가 이후

5. 규칙과 승격 기준

규칙 형식

1차의 하드코딩 규칙을 먼저 이 형식으로 옮겨 규칙셋 v1을 만들고, AI가 만든 규칙도 같은 형식을 씁니다. 조건은 최대 3개입니다.

{
  "id": "R-L2-0012", "version": 1, "layer": "L2",
  "condition": {"all": [
    {"feature": "click_offset_stdev_ms", "op": "<",  "value": 5},
    {"feature": "accounts_per_dfp",      "op": ">=", "value": 4}
  ]},
  "action": "DEFER", "mode": "shadow",
  "origin": "lgbm→tree-depth3",
  "evidence": {"sim_human_fp": 0, "new_bots_caught": 27, "fidelity": 0.91},
  "expires_after_events": 2, "approved_by": null
}

설계서 예시의 "오픈 후 반응 80ms 미만"은 7절의 이유로 "여러 번 클릭 시점의 일정함"으로 바꿨습니다. 수치는 예시입니다.

생명주기

후보 → 저장 로그로 재현 → 섀도(최종평가에서는 학습에 안 쓴 로그로 대체) → 운영자 승인 → 만료(오픈 2회 후) 및 재평가. 처분은 LOG → DEFER → BLOCK 순서로만 올립니다. 모든 판정 로그에 규칙 ID와 규칙셋 버전을 남깁니다.

6. 검증 설계 (참가자 없이)

사람 참가자를 모집할 수 없으므로, 규칙이 보는 정보를 세 종류로 나눠 각각 사람 없이 구합니다.

정보 종류예시사람 데이터 출처
환경헤더, UA, 기기 지문팀원 실기기 6대(휴대폰 2, 아이패드 2, 노트북 2) × 여러 브라우저. 사람이 아니라 브라우저·OS에 달린 값이라 기기 종류가 중요. 기록 페이지에 한 번씩 접속하면 자동 수집
행동클릭 시점, 새로고침 빈도, 노린 좌석 수문헌 수치: 반응 시간(Woods 2015), 예측 가능한 신호에 먼저 누르는 경향(Repp 2005), 실제 티켓 오픈 새로고침 빈도(ShmooCon). 출처와 숫자는 실험 전에 고정
계정계정 나이, 기기당 계정 수, 공유 IP까다로운 정상 사례를 일부러 넣음: 가족 한 기기 3계정, PC방·학교 공유 IP, 막 가입한 진짜 팬

봇 사다리

수준내용용도

L5다계정, 대전·판교로 분산 접속학습 + 보강안 ② 검증
L4LLM 브라우저 에이전트비용 때문에 제외 또는 1회 시연

실험 흐름 (규칙 진화 라운드)

  1. 사전 등록: 사람 수치 출처, 승격 기준, 실험 절차를 git에 커밋
  2. 1라운드: 사람 시뮬레이터 + 봇 L0~L2, L5로 격리 환경에서 티켓 오픈 (규칙셋 v1)
  3. 서울: 학습용 로그로 LightGBM 학습 → 깊이 3 규칙 압축 → 검증용 로그로 재현
  4. 2라운드: 처음 보는 봇(L3) + 규칙을 보지 않은 팀원이 만든 변형 봇
  5. 비교: 봇 좌석 점유율, 사람 오탐, 수준별 탐지, 압축 충실도
  6. 민감도 분석: 사람 시뮬레이터를 점점 극단으로(더 빠르게, 더 자주) 밀어서 규칙이 사람을 막기 시작하는 지점을 찾고, 사람 범위와의 거리를 보고
  7. 마지막 확인: 팀원 실기기로 직접 예매해 한 명도 안 막히는지 확인

결과를 믿게 만드는 장치

  • 사전 등록: 커밋 시각이 "결과를 보고 기준을 바꾸지 않았다"는 증거
  • 정답표는 로그 밖에: 로그·헤더에 봇 표시가 섞이면 결과가 가짜가 됨
  • 봇 만드는 사람 ≠ 규칙 만드는 사람: 2라운드 변형 봇은 규칙을 안 본 팀원이 제작
  • 격리 환경: 운영 중인 판교·대전이 아닌 별도 환경. 데이터셋은 해시로 고정해 재현 가능
  • (선택) 외부 데이터 확인: ITI 공개 데이터셋에서도 "압축 후 성능 유지"가 나오는지 확인

발표에서 먼저 말할 한계

  • 사람 시뮬레이터도 프로그램이라 시뮬레이터 특유의 버릇을 학습할 위험이 있습니다. 피처를 세 종류로 제한하고 실기기로 따로 확인합니다.
  • 사람 행동 수치는 문헌 기준이라 실제 티켓팅과 다를 수 있습니다. 민감도 분석으로 여유를 보여줍니다.
  • 봇을 우리가 만들었으므로 결과는 "통제된 실험의 상한"입니다.
  • 사람과 똑같이 행동하는 봇은 원리상 못 잡습니다. 목표는 공격 비용을 높이는 것입니다.

7. 조사로 바뀐 설계

① 반응 시간 규칙 → 일정함 규칙

티켓 오픈은 카운트다운이 있어서 사람은 반응하는 게 아니라 미리 맞춰 누릅니다. 예측 가능한 신호에는 수십 ms 먼저 누르는 경향이 있습니다(Repp 2005). "반응 80ms 미만 = 봇"은 열심히 준비한 팬을 막습니다. 대신 여러 라운드에 걸친 클릭 시점의 흔들림을 봅니다. 사람은 매번 들쭉날쭉하고, 봇은 거의 같습니다.

② 빈도 제한은 오픈 직전을 따로

ShmooCon 실제 오픈에서 직전 10초간 IP 948개가 초당 1,295번 새로고침했습니다(IP당 평균 약 1.4회/초). 현재 1차 기준 "10초 30회"(3회/초)는 경계선입니다. 오픈 직전과 평상시 기준을 나누고, nginx 제한과 역할을 정리합니다.

③ 공유 IP는 정상

ShmooCon에서 여러 장을 산 IP는 대부분 회사·학교·관공서였습니다. IP 공유만으로는 봇 근거가 안 됩니다. 시뮬레이터에 공유 IP 정상 사례를 넣습니다.

④ 기기 지문 의존 줄이기

기기 지문은 브라우저가 계산해 보내는 값이라 봇이 매번 바꿀 수 있습니다. "기기 하나에 계정 30개" 시나리오만으로는 L5에 쉽게 뚫립니다. 보강안 ②의 묶음 탐지로 보완합니다.

HTTP의 한계: Sec-Fetch-*, Client Hints는 HTTPS에서만 브라우저가 보냅니다. HTTP로 가면 L1~L2 봇을 잡을 수단이 크게 줄어듭니다. 기기 지문 계산 방식도 바뀌므로, HTTPS로 간다면 데이터 수집 전에 전환해야 합니다.

10. 예상 질문

AI가 결국 if문 아닌가요?
모델은 서울에서 LightGBM으로 학습하고, 판정에는 그 모델을 압축한 규칙만 내려보냅니다. 압축 후에도 모델이 잡은 봇의 몇 %를 유지하는지 수치로 보여드립니다. 실시간 경로에 모델을 넣지 않은 것은 지연과 설명 책임 때문에 의도한 설계입니다.
사람 데이터 없이 오탐을 어떻게 아나요?
헤더는 실제 기기에서, 행동은 문헌 수치에서 가져와 사람 시뮬레이터를 만들었습니다. 시뮬레이터를 극단까지 밀어서 규칙이 사람을 막기 시작하는 지점을 찾고, 그 지점이 사람 범위에서 얼마나 떨어져 있는지 보고합니다. 마지막으로 실제 기기로 직접 예매해 확인했습니다.
봇도 사람도 직접 만들었으면 결과가 유리하게 나오지 않나요?
기준을 실험 전에 커밋했고, 2라운드 봇은 규칙을 보지 않은 팀원이 만들었으며, 학습에 쓰지 않은 봇 수준(L3)으로 평가했습니다. 결과는 통제된 실험의 상한이라고 밝힙니다.
빨리 누르는 진짜 팬이 봇으로 걸리지 않나요?
반응 속도 자체는 판단에 쓰지 않습니다. 카운트다운이 있으면 사람도 미리 맞춰 누르기 때문입니다. 대신 여러 번에 걸쳐 "기계처럼 똑같은지"를 봅니다. 그리고 처분은 결제 보류부터 시작해 좌석을 바로 빼앗지 않습니다.
상용 봇 차단 서비스와 무엇이 다른가요?
탐지가 공정성 판정 순서를 건드리지 않는 구조(실험 C), 전국 PoP 로그를 KOREN으로 모아야만 보이는 분산 봇 탐지, 판정 근거의 기록·재현입니다.
