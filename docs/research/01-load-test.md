# 부하 측정: 기존 방식 vs Redis 1단계 vs Redis 2단계

측정일: 2026-10-13

## 비교 대상

| 모드 | 설정 | 동작 |
|---|---|---|
| 기존(메모리) | `STATE_BACKEND=memory` | 수집창을 각 워커 메모리에 둔다. 확정마다 DB INSERT 1회 → 확정 방송 |
| Redis 1단계 | `STATE_BACKEND=redis`, `REDIS_DB_BUFFER=0` | 수집창을 Redis에 둔다(Lua로 원자 처리). 확정마다 DB INSERT 1회 → 확정 방송 |
| Redis 2단계 | `STATE_BACKEND=redis`, `REDIS_DB_BUFFER=1` | 창 마감 Lua가 확정 기록 + Redis Stream 적재 + 방송 대기 등록을 한 번에 수행. 방송은 DB를 기다리지 않고, DB는 50ms 동안 모아(최대 500건) 한 번에 INSERT |

## 측정 환경

- 운영 시스템과 분리된 격리 환경(별도 docker 네트워크)에서 Kafka·Postgres·Redis·central을 따로 띄웠다. 운영 시스템에는 테스트 요청을 보내지 않았다.
- central 설정은 운영과 동일: 워커 3개, Kafka 파티션 3개, DB 풀 16, 수집창 3000ms 고정, `ALL_REQUESTS_KEEP=40`.
- 판교 서버 1대(16코어)에서 부하 발생기와 대상이 함께 돌았다. 네트워크 지연은 포함되지 않는다.
- 측정 후 테스트 컨테이너·네트워크·이미지는 모두 삭제했다.

## 1. 대량 동시 확정 (좌석마다 요청 2건을 한꺼번에 투입)

숫자는 **3초 창이 닫힌 뒤 마지막 좌석의 확정 방송이 나가기까지 더 걸린 시간**이다.

| 좌석 수 | 기존(메모리) | Redis 1단계 | Redis 2단계 |
|---|---|---|---|
| 608석 (공연장) | 0.55초 | 0.73초 | **0.25초** |
| 5,000석 | 2.0초 | 2.6초 | **1.75초** |
| 20,000석 (경기장급) | **약 1/3 확정 실패** | 21.8초, 전부 확정 | **15.7초, 전부 확정** |

추가 관찰:

- **Redis 2단계는 DB 쓰기 횟수를 2만 회에서 약 200회로 줄였다.** 배치 1회 평균 11~19ms.
- **기존 방식은 2만 석에서 좌석 확정이 사라졌다.** 두 번 실행해 각각 6,342석, 9,053석이 확정되지 않았다. 승자는 정해졌지만 DB 저장과 방송이 안 된 상태다.
  - 원인은 DB가 아니라 **central CPU 포화**였다. 워커 3개가 3코어를 100% 쓰는 동안 Postgres CPU는 거의 0%였다. CPU가 꽉 차 DB 연결을 5초 안에 얻지 못해 저장이 3회 모두 실패했다.
  - 기존 코드는 새 좌석이 열리거나 닫힐 때마다 전체 좌석을 훑어 지표를 계산하고(좌석 수의 제곱에 비례), 요청마다 pending 방송을 따로 보낸다. 좌석이 많을수록 CPU를 크게 쓴다.
  - 따라서 "DB가 버거워서 배치가 필요하다"보다 **"DB를 기다리는 동안 판정 서버가 막힌다"**가 정확한 설명이다.
- **Redis 2단계의 남은 병목:** 2만 개 창이 동시에 닫힐 때 central→Redis 연결 풀(32개)이 모자라 3,318석의 마감이 한 번 실패했다. 청소기가 0.5초마다 100석씩 다시 닫아 전부 확정됐지만 그래서 15.7초가 걸렸다. 연결 풀을 늘리거나 청소기 처리량을 늘리면 줄일 수 있다.

## 2. 최대 소화 속도 (요청 60만 건을 미리 쌓은 뒤 central 기동)

| 기존 | Redis 1단계 | Redis 2단계 |
|---|---|---|
| 초당 15,365건 | 초당 16,548건 | 초당 16,508건 |

세 모드가 거의 같다. Redis 도입은 요청 소화 속도를 바꾸지 않았다. 병목은 Kafka 메시지를 읽고 JSON을 해석하는 파이썬 처리다.

참고: 부하 발생기 1개는 초당 약 2.1만 건까지 보낼 수 있다. 608석 기준 초당 2.1만 건을 10초 보냈을 때 Redis 2단계의 확정 추가 지연은 p50 62ms, p95 101ms였다.

## 3. PoP(사용자가 처음 닿는 서버) 처리량

PoP 1개(워커 4개)가 CPU 4코어를 다 쓸 때의 처리량:

| 요청 | 초당 처리량 |
|---|---|
| 좌석 클릭 `POST /seat-request` (익명) | 약 2,140건 |
| 좌석판 조회 `/seats-overview` (응답 약 12KB) | 약 1,430건 |
| 남은 좌석 수 `/seat-count` | 약 2,700건 |
| 클릭 결과 확인 `/seat-status/{id}` | 약 2,780건 |
| 시계 정보 `/clock-offset` | 약 2,600건 |

**central(초당 1.6만 건)보다 PoP가 약 8배 먼저 막힌다.** 시스템 전체의 병목은 PoP다.

## 4. 수용 인원 추정

좌석 화면(`seat.html`)은 열려 있기만 해도 1.5초(좌석판), 3초(남은 좌석), 5초(시계)마다 PoP에 묻는다. 사람당 초당 약 1.2회다. 좌석을 누르면 결과가 나올 때까지 0.5초마다 다시 확인한다.

- 화면만 열어 둔 사용자: PoP 1개가 약 1,500명에서 CPU 100%
- 1분에 3번쯤 클릭하는 사용자까지 섞으면 100%에 약 1,200명, 여유를 둔 70% 기준 **PoP당 약 800~1,000명**
- **판교 + 대전 두 PoP 합계 약 1,600~2,000명 동시 접속** (대전 서버가 판교와 같은 성능이라는 가정)

한계: 비로그인 요청 기준(실제로는 토큰 검증 비용이 조금 더 붙는다), 네트워크 지연 제외, 사용 패턴은 가정값이다.

## 5. 대규모 트래픽을 감당하는 서비스와의 구조 차이

| 항목 | 대규모 서비스 | DOON 현재 |
|---|---|---|
| 입장 조절 | 대기열로 감당 가능한 만큼만 입장 | 없음 |
| 캐시 | 좌석판처럼 모두 같은 응답은 CDN/nginx가 0.5~1초 저장 | nginx 캐시 꺼짐, 조회가 모두 PoP까지 감 |
| 상태 전달 | WebSocket/SSE로 서버가 변경분만 push | 1.5~5초 polling |
| 앞단 확장 | 로드밸런서 + 오토스케일로 수십~수백 대 | 지역별 PoP 컨테이너 1개(워커 4) — 상태가 거의 없어 늘리기 쉬운 구조 |
| 판정 확장 | 좌석/구역 단위 샤딩 | Kafka 파티션 단위 분할 — 같은 원리, 파티션·워커를 늘리면 확장 |
| 비정상 요청 | 봇 차단·요청 제한·로그인 필수를 앞단에 | 봇 필터 monitor 모드, 로그인 선택 |

뼈대(앞단과 판정의 Kafka 분리, 좌석 단위 분할, 판정 상태 Redis 분리, DB 배치)는 대규모 시스템과 같은 방향이다. 부족한 것은 대기열·캐시·push·확장 설정이며 모두 앞단 문제다.

발표용 문장(제안): "현재 데모 구성은 PoP당 약 1천 명입니다. PoP는 상태가 없어 대수만 늘리면 되고, 판정은 좌석 단위로 나뉘어 있어 파티션을 늘리면 확장됩니다. 상용화 단계에서는 대기열과 캐시를 앞단에 두는 것이 다음 단계입니다."

## 남은 정리 사항 (2026-10-13 기준)

- Redis 2단계 코드는 판교에서 켜져 있지만 커밋되지 않았다. `.env`에 `REDIS_DB_BUFFER=1`이 없어 compose를 다시 올리면 꺼진다.
- 2단계는 확정 방송이 DB 저장보다 먼저 나간다. Redis가 방송 직후 1초 안에 죽으면(AOF everysec) 확정이 Redis와 DB 양쪽에서 사라질 수 있다. 대안: `appendfsync always`, 또는 DB 저장 후 방송.
